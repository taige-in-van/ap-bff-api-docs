POS 终端 — 终端面契约 (1.0.0)

Download OpenAPI specification:

现网已安装的 POS 应用调用的接口：Clover、Sunmi 系原生应用（下称原生端），以及 Ingenico 键盘机上的网页应用（下称键盘机）。除核销四个接口（getVoucher、redeemVoucher、listRedemptions、updateRedemptionRemark）外，地址、请求头、请求体与响应的形状都与现网一致，端不需要升级；核销几页要随新接口改版。

凭据

  • 登录前的接口（图形验证码、登录、登记本机）不带凭据。
  • signIn 返回临时登录凭据 sign_key，有效 30 分钟，只用于登记本机，有效期内可重复使用。
  • registerDevice 返回 dev_id 与设备密钥 auth_code。同一台设备每登记一次，设备密钥换新，旧的作废。一台终端只属于一个商户。
  • 此后每个请求都带四个头：Merchant-Id、Device-Id、Device-Type、Global-Sign，缺一不可。请求不带令牌，服务端按设备认出它当前由哪个账号登录；这份登录没有有效期。
  • Global-Sign 是把 dev_id、auth_code、请求路径用 & 连起来后算出的 SHA-256 十六进制串。请求路径是端发出时的完整路径，从 /api 起，不含查询参数。比对不分大小写，不一致即拒绝。
  • 另接受 Device-Version（应用版本号）与 Device-Token，以及一组旧头名 client_id、device_id、client_type、device_version、device_token，都不是必需的。其他头（如 Clover 版另发的 royalpay_sign）不读。

设备上的登录在下列情况失效，失效后须重新登录并登记本机：

  • 同一台设备再次登录或登记本机。
  • 该账号修改了密码（任何入口，含找回密码重置）、被停用，或被移出商户。
  • 设备被停用或解绑。
  • 商户被冻结。

同一账号可以同时在多台设备上登录，互不影响。

响应外壳

  • /retail_valid/、/retail/、/vouchers/ 与 /redemptions 下的接口，成功响应是裸 JSON，没有外壳。
  • 失败响应的 HTTP 状态不是 2xx，响应体是 { status, message, data, timestamp, traceId, code }：status 与 HTTP 状态相同，message 是可以直接展示的文案，data 为 null，code 是整数错误码。

状态码

失败只用下面三档，其余 4xx 不使用。

HTTP 状态 情形
401 需要重新登录：设备上的登录失效、缺凭据头、设备未登记、签名不一致、设备被停用、商户被冻结、设备类型不认识
400 登录、登记本机被拒（含上一行的原因在这两步仍然存在）；权限不足、参数不对、状态不允许、操作太频繁等业务性拒绝
5xx 服务端故障

401 的 code，每个受保护的接口都可能返回，各接口说明里不再重复：

  • 206014 设备未登记、需要重新登记，或设备上的登录已失效；缺 Merchant-Id、Device-Id 头同此。
  • 206015 Global-Sign 与服务端算出的不一致，或没带。服务端可配置为对「不一致」只记录、不拒绝；没带 Global-Sign 时始终拒绝。
  • 206016 Device-Type 不是受支持的终端类别。
  • 208033 设备已被停用。
  • 208028 商户已被冻结。

400 的 code 见各接口说明；说明里没点名的（参数不合法、操作太频繁等）按 message 处理即可。失败响应可能另带 context，内容与登记该码的码表所写相同。

权限按商户后台的权限点判，不看角色，各接口标在 x-required-privilege；员工可以同时持有多个角色，权限取并集，Owner 拥有全部权限。标 session 的接口只要求已登录。预设角色里的店长、收银员都有收款、查单与核销所需的权限。权限不足属于业务性拒绝，返回 400，message 写明需要商户后台的哪项权限。

找回密码

POS 上不承接找回密码。现网版本的找回密码入口（/api/v1.0/app/device/forget/verify 与找回流程其余各步）不再受理，回 HTTP 400、code 为 208037、顶层 message 为固定的双语提示「暂不支持在 POS / App 上重置密码，请联系 Owner 在商户后台重置 / Password reset is not available on POS / App, please ask your Owner to reset it in the Merchant Portal」。

仅查看状态

商户被设为仅查看时，除登录与登记本机外，改状态的请求返回 400、code 为 208035；查询照常。

账号、密码加图形验证码登录

校验图形验证码与账号密码，通过后返回账号与商户信息，以及用于登记本机的临时登录凭据 sign_key（有效 30 分钟）。登录不要求二次验证，账号在商户后台开了验证器的也一样。

loginId 先按用户名精确匹配，匹配不到再按邮箱，不分大小写。

登录所在的商户默认按登录账号定：Owner 与主商户的员工为主商户，关联商户的员工为其所属的关联商户。响应里的 client_id、client 就是这个商户；这个商户被冻结或删除时登录被拒，不改落其他商户。请求带了 devId、且该设备已登记在登录者可以访问的某个关联商户名下时，登录就在该商户，client_id、client 返回它；没带 devId 的，在 registerDevice 那一步转到该商户。

下列情形返回 400：

  • 204020 图形验证码不对，或已过期、已用过。
  • 206012 账号不存在或密码不对，两者不区分。
  • 966001 连续登录失败次数过多，账号被锁定。默认连续错 5 次锁 15 分钟（可配置），与商户后台网页登录、商户 App 登录共用计数。
  • 906004 同一登录名（解析不到账号）短时间内失败过多，稍后再试。默认 15 分钟内 5 次（可配置），与商户后台网页登录、商户 App 登录共用计数。
  • 208027 账号已被停用。
  • 208029 账号的邮箱还没有验证。
  • 208028 登录所在的商户已被冻结或删除。
  • 208033 带了 devId，而这台设备已被停用。

登录后按终端序列号登记本机，取得设备凭据

凭 signIn 返回的 sign_key 登记这台终端，返回 dev_id 与设备密钥 auth_code。同一商户下同一序列号、同一终端类别再次登记时，dev_id 不变，设备密钥换新、旧的作废，设备上原来的登录随之失效。sign_key 在有效期内可以重复用于登记。

登记到哪个商户：这台终端（按序列号）已登记在登录者可以访问的某个关联商户名下时，以该商户为当前商户；否则登记到登录所在的商户名下。响应里的 client_id 就是设备所属的商户。一台终端只属于一个商户，已登记在其他商户名下的，要原商户在商户后台解绑后才能登记到新商户。

请求体是一段 Base64 文本，由下面这份 JSON 加密而来：

  • client_device_id：终端序列号。
  • sign_key：signIn 返回的临时登录凭据。

加密方案按端分两种，密钥由服务端按 devType 选取：

方案 用它的端 算法
A 原生端（clover、sunmi、poynt、pax、ingenico_android、cashier_pos） AES-128，ECB 模式，PKCS5 填充，密文为标准 Base64
B 键盘机（ingenico） AES-128，CBC 模式，固定 IV，明文用零字节补齐到块长，密文为标准 Base64

下列情形返回 400：

  • 206016 devType 不是受支持的终端类别。
  • 206014 sign_key 无效或已过期，须重新登录。
  • 108014 设备已登记在其他商户名下（不是登录者可以访问的商户）。
  • 108015 这台设备已被停用。
  • 108018 上报的终端序列号不能用作设备标识（为空，或是运行环境返回的固定占位值）。
  • 208028 商户已被冻结。
  • 请求体解不开，或解开后缺 client_device_id、sign_key。

扫顾客的付款码收款

收银员扫到顾客的付款码后调用。服务端认出付款码属于哪个支付方式品牌，建订单，再向渠道下单，等到渠道的首次应答后返回订单号与当时的订单状态；渠道迟迟不应答时同样返回订单号。最终结果以 getOrder 查到的为准。下单后默认 60 秒内（可配置）没有结果的，订单关闭（status 为 3）。

退款（原生端的调法）

对一笔订单发起退款。服务端落退款单、提交渠道，拿到渠道的首次应答后返回；返回时退款是处理中或已成功，端不用轮询。键盘机用 POST 调同一路径（refundOrderByPost），服务端行为相同。

  • 退款密码：要求本设备本次登录已通过 verifyRefundPassword（有效到该设备下次登录为止）。退款可能由终端自带的收银应用拉起、不经过本应用密码页的终端类别不查这一条，按 Device-Type 识别；目前属于这一类的是 poynt 与 ingenico。
  • 金额：amount 以分计，整数或数字字符串都收。币种是订单的币种，不用传。
  • 可退金额：顾客实付总额（金额、小费与顾客承担的手续费之和）减去已退金额。允许部分退、多次退。
  • 能退哪些订单：当前商户及其子商户的订单。子商户的订单还要运营开了「父商户可退子商户订单」，没开按不存在处理。
  • 挂起中的预授权订单（getOrder 的 pre_auth 为 1）不能直接退款，须先 releasePreauth，释放后再退。
  • 资金：商户可用于退款的资金不够时返回 400，message 说明余额不足（含 balance）。
  • 审核：命中审核规则（金额达到审核阈值、成交超过退款周期、当日退款笔数超限）的退款进入审核、不立即退，返回 400，message 说明已提交审核；审核通过后由服务端完成退款。审核中的退款不计入 getOrder 的 refund_fee，也不出现在 refund_logs。
  • 重复提交：同一台设备对同一订单、同样金额的重复退款请求在 60 秒内（可配置）视为同一笔，返回第一次的结果；首次请求还在处理时到达的重复请求，等首次结果出来后返回同一结果。60 秒后同样金额再退是新的一笔。

  • 108025 这笔退款不予受理，不细分原因：订单没有支付成功、已全额退、金额不是正数或超过可退金额、成交超过最大退款期限（可配置）、商户的退款能力被关闭、订单是挂起中的预授权订单等。
  • 108017 同一登录账号对同一订单在极短时间内重复提交（不论金额）。
  • 208035 商户处于仅查看状态，不能退款。
  • 本设备本次登录还没有通过退款密码校验（退款可由终端自带收银应用拉起的终端类别除外，目前是 poynt 与 ingenico）。
  • 当前账号没有发起退款的权限。
  • 订单不存在，或不在能退的范围内。
  • 资金不足，message 说明余额不足。
  • 进入审核，message 说明已提交审核。

所选区间或单笔交易的打印数据
