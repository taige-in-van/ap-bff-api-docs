商户后台 收款产品 — 前端契约面 (2.2.1)

Download OpenAPI specification:

商户后台 React SPA 消费的收款产品契约：店铺码与其收款页设置、账单、Product Links（商品 / 票务 / 礼卡）及其销售单、收款设置（订单有效期、客户服务费开关）与收银台支付方式候选。 浏览器持 httpOnly 会话 cookie，字段类型与校验规则以本 spec 各字段为准。

幂等 / CSRF 口径：

  • 创建类与命令类（建账单、建与改 Product Link、销售单的重发 / 作废 / 风控处置）挂 Idempotency-Key，同一次提交的网络重试用同键返回首次结果；天然幂等的纯 PUT / DELETE 不挂。
  • cookieAuth 的非安全方法一律带 X-CSRF-Token。
  • 当前商户以会话为准、不看请求体；当前商户不可访问时返回 409·208022。

店铺码

店铺码：各个码（二维码由前端按承载原文生成）、店铺码收款页设置（Logo、小费、付款人采集项、支付方式、附加说明）。

读店铺码的各个码（第 1 项是主码）

当前商户的店铺码，按结算币种以及 CNY 标价、预授权、银联码的开通情况给出各个码。第 1 项是主码（优先结算币种的标准码，该码不可用时由服务端在可用的码里定），其余按返回顺序排列；一个码都没有时返回空数组。

保存店铺码收款页设置

保存店铺码收款页设置与商户小费配置，只提交要改的。

  • 带了 checkoutOptions 时至少 1 项（空 → 400·204005）。相对已保存的集合新加的项须已开通（listCheckoutOptions 里 opened 为 true），否则 → 409·208007；已选着、后来停用的项可以原样保留，付款人看不到它，重新开通后即恢复。
  • 带了 payerInputKeys 时提交保留下来的完整键列表；缺了必填项、或自撰标题以 sys: 开头 → 409·208030。第一次保存时系统项按当时的系统目录固化，此后系统目录变化不追溯。
  • logoFileId 引用的文件不存在、不是本商户上传的或用途不符 → 400·208040（details 指到 logoFileId）。
  • 保存涉及收款页设置与商户小费两处，全部校验通过才写入；返回失败时原样重发同一请求体即可。

同样的请求体重发结果不变，不挂 Idempotency-Key。

创建账单

新建一张未付账单，生成付款链接，账单号由服务端分配。

  • 标价币种须是 listCheckoutOptions 里已开通项的 pricingCurrencies 之一，否则 → 400。
  • 到期日早于当天 → 400·204004。

必带 Idempotency-Key：同键 + 同请求体重发返回首次结果、不重复建单；改了请求体须换新键，沿用旧键 → 409·908003；同键的上一次提交还在处理 → 409·908002。

创建 Product Link

type 决定带哪个内容段（giftcard / product / ticket）：必须带且只带对应的那个，否则 400。各项金额的币种须等于 currency，否则 400（details 指到字段）。

  • 支付方式：新加的项须在 listCheckoutOptions（礼卡传 linkType=giftcard）里 opened 为真、且 pricingCurrencies 含 currency，否则 409·208007；一项都没选 400·204005。
  • 采集项按 key 给全（见 buyerInputKeys）：缺了必填项、或自撰标题以 sys: 开头 409·208030。
  • 政策条款不在本请求里：新链接自动带上商户当前的默认条款，之后在详情页改。
  • 礼卡：fulfillmentMode 创建后不可改；campaignEndDate 不早于今天；bonusTerms 为 custom 时 bonusNotes 必填——不满足均为 400。
  • bannerFileId、giftcard.brandLogoFileId、product.items[].imageFileId 引用的文件不存在、不是本商户上传的或用途不符 → 400·208040（details 逐项指到出问题的那个字段，如 product.items[1].imageFileId）。

幂等：同一个键改了请求体 409·908003；同键的上一次提交还在处理 → 409·908002。

礼卡订单风控处置

对礼卡订单做人工处置，当前可执行的动作看详情的 giftcard.actions.riskDispositions：

  • escalate（升为高风险）与 blacklist（加入黑名单）：订单为中风险时可用，效果相同——付款人进入礼卡购买黑名单、此后不能再买礼卡；这笔订单还没发放的不再发放，已发放的不撤回。
  • approve（放行）：订单为高风险时可用——付款人移出黑名单；订单还没发放的恢复发放。
  • remove_blacklist（移出黑名单）：付款人在黑名单里时，在他的任一礼卡订单上可用——付款人移出黑名单。

可用与否只看上面的条件，不看活动当前是否开着订单风险评估。

幂等：同键同请求体重发不重复处置；改动作要换新键，沿用旧键改动作 → 409·908003。换新键提交时风险等级已被别人改过、该动作不再可执行 → 409·208020；同键的上一次提交还在处理 → 409·908002。
