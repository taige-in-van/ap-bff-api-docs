商户后台 账户账务与清结算 — 前端契约面 (2.1.0)

Download OpenAPI specification:

商户后台 React SPA 消费的资金概览 / 账户流水 / 结算单 / 月度账单 / 退款预留金管理 / 数据导出 契约。

资金概览 / 流水 / 结算单 / 月度账单为只读；结算金额由平台资金能力产出，本面只展示、不二次计算。 储备金 Top Up / Withdraw 为资金动作，会影响后续结算；auto-replenish 的自动补足由平台触发、不在本面发起；储备金 funding（Top Up / auto-replenish 配置）经 Owner email OTP 二次验证;Withdraw 与导出不要求 OTP。

金额一律商户唯一结算币种（单商户单结算币种）；金额最小币种单位整数字符串（components Money）。字段类型以本 spec 为准。

幂等 / CSRF 口径:

  • ① 有副作用的写（储备金 funding / withdrawal、导出创建）挂 Idempotency-Key（资金路径强一致，重投返原结果）;OTP 挑战类按流程语义不挂幂等键。
  • ② cookieAuth 的非安全方法一律挂 X-CSRF-Token（double-submit，fail-closed）;无公开端点（资金面全程受 RBAC + 会话）。

鉴权 / 行级授权:所有读写均限会话当前 merchant scope（merchant 上下文从会话取、不信请求体）;储备金 funding（Top Up / auto-replenish）经 Owner email OTP（身份验证能力，资金动作二次验证）放行,Withdraw 不要求 OTP（仅内部回 Account Balance、不外流）。

状态码与错误分流一律见「API 基础约定」,本面不另立口径（按 code 分流、不按状态码;含跨 scope 资源统一 404 反枚举那条）。

account-overview

资金概览：Account Balance（商户面 = 账本可结算余额 − 应收商户款，可为负）/ To Settle（派生展示）/ Refund Reserve，商户结算币种。只读。

资金概览（Account Balance / To Settle / Refund Reserve）

资金概览（商户 scope）：Account Balance（商户面口径 = 账本可结算余额 − 应收商户款，可为负，负值 = 商户欠平台）、To Settle（按手续费结算模式派生、本面不二次计算）、Refund Reserve。

Account Balance 卡片展示值是否并入平台侧预授权挂起额由管理后台设置的 per-商户展示配置控制（默认并入,本面只展示、不改账本值）。

上游账务查询超时 → 三个金额键（accountBalance / toSettle / refundReserve）一起不返回、降级展示「暂不可用」、不伪造资金,不阻塞页面。

⚠️ 储备金写操作成功后本卡片有追赶窗口：Top Up / Withdraw 返回成功即表示资金动作已受理并有权威结果（凭响应里的操作标识），但概览与账户流水是另一次取数、可能短暂看不到这笔。按最终一致处理——刷新后没看到不代表失败，不要提示失败、更不要诱导用户再提一次（重复提交资金动作的代价是真金白银）。要确认结果就凭该操作标识重查，别靠列表有没有出现来判断。

stale-tab 一致性守卫（读写统一）：页面预期的当前商户 ID。与会话当前商户比对，一致才执行；不一致时读不返回错商户数据、写不执行，并按下面两种情形二分：

  • ① 会话有当前商户、只是与 expected 不同 → 409 · 208001（MERCHANT_CONTEXT_CHANGED），响应 context.currentMerchantId 回显服务端当前商户供前端直接 re-sync；
  • ② 会话没有当前商户（无可回显者）→ 409 · 208022（MERCHANT_NOT_ACCESSIBLE），前端重跑启动链路按 routeTo 分流（见 API 基础约定「merchant scope + stale-tab 守卫」）。

挂在所有依赖当前商户的读 + 写接口；前端统一 interceptor 发送 + 处理 409（提示并刷新当前商户）。

豁免：不依赖「当前商户」的接口——当前商户的 re-sync / 切换入口本身，以及目标由 path 直接指定、与当前商户无关的接口。

account-ledger

账户流水（Account Ledger）：每笔资金进出只读分页查询（过滤 + 搜索 + 双池可见）。只读。

账户流水查询（过滤 + 搜索 + 分页，只读）

账户流水（商户 scope）：按 postedAt 倒序稳定分页（不要按 occurredAt 重排，会打乱余额顺序）;postedAt 相同的行按 entryId 倒序,以此保证翻页不重不漏。

⚠️ balanceAfter 只在同一资金池内逐行衔接——pool 缺省时两池分录交错返回，相邻两行往往属不同池，跨行相减必然对不上（Top Up / Withdraw / auto-replenish 每笔都同时产两池各一行、postedAt 常完全相同）。要连续的余额走势就带 pool 筛或按池分组渲染;不要把「上一行余额 = 本行 balanceAfter − amount」写成客户端校验。

每行含资金池 / 类型 / 带符号金额 / 对应资金池变动后余额 / 关联单据或操作记录。空结果返回空态、不报错。

不传日期参数 = 不按日期筛（返回全部流水，无默认时间窗）。

settlement

结算单（Settlement）：按清算周期 / 状态查列表 + 逐笔结算影响明细详情。只读。

结算单列表（周期 / 状态过滤 + 搜索 + 排序 + 分页）

结算单列表（商户 scope）。排序走 sortField + sortOrder（页面默认最新结算在前由前端显式传）;状态过滤为商户视角四态（待结算 / 处理中 / 已结算 / 失败,不展示具名冻结态）。 FAILED 行标记并提示资金退回待结算池、后续重新归集或人工处置。不传日期参数 = 不按日期筛（返回全部结算单，无默认时间窗）。

失败一律按 code 分流（不按状态码；本 op 承诺的码见 x-error-codes，逐个含义查随包码表）：

  • 验证码错、但仍有剩余次数 → 400·204010（剩余次数在 context.attemptsRemaining,留在弹窗重输）;
  • 尝试超限锁定 → 423;
  • 提交摘要与该 challenge 绑定的摘要不一致、或不是发起该挑战的那个会话 → 403·206005（防串改金额 / 夹带配置——须重走一次 OTP,不是重输验证码）;
  • 无权限 → 403、无业务码。

以上任一失败,Top Up 与配置两者都不生效。限流 → 429（发码冷却是 requestRefundReserveOtp 的事,不在本 op）。

两条线分开看——上方那串 4xx 是受理前就被拒（参数 / OTP / 幂等 / 限流），什么都没发生；受理之后的执行结果一律 200 + 子项 status，包括执行期失败（如 Account Balance 余额不足）——由 topUpResult.status=FAILED + failureReason 表达,按 failureReason 取值分支,别假定只有余额不足一种。 余额是活值、只能在执行时判，所以它落在受理后这条线上；别把它接到 error 分支，否则余额不足时前端什么都不提示。

执行顺序固定：先 Top Up、再存 auto-replenish 配置，因此终态只有三种——

  • 〔1〕Top Up 成功 + 配置成功;
  • 〔2〕Top Up 成功 + 配置失败（部分失败）;
  • 〔3〕Top Up 失败 → 配置不执行（autoReplenishResult.status=NOT_EXECUTED）。

「Top Up 失败而配置成功」不会出现。未达终态时子项为 PENDING,凭 operationId 轮询收敛。 auto-replenish 只是保存配置（其自动补足执行由平台在 Refund Reserve 低于阈值时触发,不在本次写内）。

幂等：必带 Idempotency-Key。本 op 的幂等指纹只覆盖操作摘要（topUpAmount + autoReplenish），不含 otp——这是对公共约定「改了请求体就必须换新键」的显式例外，因为验证码错时的规定动作就是原地重输。 据此,两种重试都复用同一个键，但走向不同、别混。怎么判自己在哪支：只有收到 4xx 响应体才是 ①；其余一切——超时 / 没收到响应 / 5xx / 已拿到过 200——都走 ②。

  • ① 受理前被拒（任何 4xx——验证码错、摘要或会话不符、挑战过期、尝试超限、参数被拒——此时什么都没发生）：按该码的规定动作处置后复用原键重投（哪怕规定动作是「回第一步重走 OTP」,那仍是同一次提交意图、不换键）;本 op 会重新校验新验证码、不因幂等键相同而跳过。
  • ② 受理与否不确定 / 已受理（网络超时、响应丢失、5xx、或已拿到过 200）：复用原键重投——已受理则直接返首次结果、不会重复划转,也不会再去校验验证码（故不应因此收到 410）;未受理则正常受理。

5xx 明确归这一支：它不是「没发生」的证据，写有可能已经落下。别向用户断言「未划转」，也别指望 getReserveOperation 兜底——5xx 响应里没有 operationId，此时唯一可靠的退路就是同键重投。

⚠️ 最危险的误判：受理前失败里有几种的规定动作是「回第一步重新发起」,重走一遍 OTP 弹窗看起来很像「新意图」——它不是。只要金额与配置没改,就仍用原键;因为「验证码已消费 / 挑战过期」而换新键重发,才是真正的重复划转风险。

改了金额或配置就必须换新键,沿用旧键改摘要 → 409·208005、且不推进。 正面判据：一次提交意图一个键——用户重开弹窗 / 重新确认即换新键（同额再充一笔也要换,否则会命中首次结果、第二笔实际没发生）;同一意图内的重试（验证码重输、网络重试）复用同键。

stale-tab 一致性守卫（读写统一）：页面预期的当前商户 ID。与会话当前商户比对，一致才执行；不一致时读不返回错商户数据、写不执行，并按下面两种情形二分：

  • ① 会话有当前商户、只是与 expected 不同 → 409 · 208001（MERCHANT_CONTEXT_CHANGED），响应 context.currentMerchantId 回显服务端当前商户供前端直接 re-sync；
  • ② 会话没有当前商户（无可回显者）→ 409 · 208022（MERCHANT_NOT_ACCESSIBLE），前端重跑启动链路按 routeTo 分流（见 API 基础约定「merchant scope + stale-tab 守卫」）。

挂在所有依赖当前商户的读 + 写接口；前端统一 interceptor 发送 + 处理 409（提示并刷新当前商户）。

豁免：不依赖「当前商户」的接口——当前商户的 re-sync / 切换入口本身，以及目标由 path 直接指定、与当前商户无关的接口。
