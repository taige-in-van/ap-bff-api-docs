商户后台 商户与入驻 — 前端契约面 (2.3.3)

Download OpenAPI specification:

商户后台 React SPA 消费的商户与入驻契约：登录者能进的商户（列表、新建关联商户、删除未激活的关联商户）与每个商户的入驻申请（加载、分步保存、上传文档、提交审核）。各步的候选集取系统契约的 /config/*；切换当前商户见认证契约的 switchCurrentMerchant。 浏览器持 httpOnly 会话 cookie，字段类型与校验规则以本 spec 各字段为准。

幂等 / CSRF 口径：

  • 新建关联商户挂 Idempotency-Key，同一次提交的网络重试用同键返回首次结果；删除关联商户天然幂等、不挂。
  • 入驻申请的分步保存（PUT）与提交（重放命中已提交态返回相同结果）天然幂等，不挂；文档上传非幂等，每次产生新 fileId。
  • cookieAuth 的非安全方法一律带 X-CSRF-Token。

按路径定位商户：入驻申请按路径里的 merchantId 定位（一个商户一张入驻申请），不看会话的当前商户：首次入驻取 getCurrentSession 的 merchantId，关联商户取 createMerchant 返回或商户列表里的 merchantId。商户须是登录者名下的商户（登录者所属的商户，及其所属主商户名下的关联商户），已删除 → 404；入驻被拒、已冻结的商户不在商户列表里，但申请仍可读。

商户

商户：登录者能进的商户列表、新建关联商户（BRANCH / NEW_LEGAL_ENTITY，一律挂在主商户下）、删除未激活的关联商户。

商户列表（顶栏切换器、启动链路）

登录者能进的商户：Owner 是名下全部商户；主商户的员工是主商户加它名下的全部关联商户（切过去用同一个角色）；关联商户的员工只有本商户。再排除已删除、已冻结和入驻被拒的。主商户排第一，关联商户按创建时间排在后面。 被拒的商户不在本列表，但它的入驻申请仍可按 merchantId 读。

  • 已激活的商户 status 为 ACTIVE；未激活的返回入驻申请的状态（DRAFT / UNDER_REVIEW / MORE_INFO_REQUIRED）。
  • 当前商户以 getCurrentSession 的 merchantId 为准，本接口不返回。
  • 代登会话只列被代的那个商户。

新建关联商户

建一个关联商户和它的入驻申请草稿（DRAFT），返回 merchantId。不改变会话的当前商户。

  • 只有 Owner 能调，其他人 → 403。
  • 以会话当前商户为发起商户：当前商户未激活或不可访问 → 409·208022。
  • 新商户一律挂在主商户下面、Owner 同主商户，不论当前商户是主商户还是关联商户。
  • 所属主商户已冻结 → 409·208054，不建商户也不建申请。
  • BRANCH 按主商户的资料预填，NEW_LEGAL_ENTITY 只预填 Contact 步（含推荐来源）与本请求里的字段；预填结果在入驻向导读申请时返回。
  • country 与 currency 须是 /config/currencies 里的一条组合，否则 400。

幂等：必带 Idempotency-Key。同键 + 同请求体重发返首次结果、不会重复建商户；改了请求体就必须换新键，沿用旧键改内容 → 409·908003。

删除未激活的关联商户

删除一个还没激活的关联商户：商户标记删除，在途的入驻申请撤回。删除后不再出现在商户列表里，填过的资料不能恢复。

  • 只有 Owner 能调，其他人 → 403。
  • 已激活（含已冻结）的商户 → 409·208003；
  • 入驻被拒的商户 → 409·208003；
  • 主商户 → 409·208024；
  • 工作人员代为建档的待激活商户 → 409·208046（撤回由工作人员办理）；
  • 商户不存在、或不是登录者名下的商户 → 404（已删除的按下面的幂等规则返回 204）。

幂等：已删除的商户再删返回 204，不挂 Idempotency-Key。

分步保存一个步骤

mode=next 校验本步完整后保存；mode=draft 只校验已填字段的格式、放宽必填。settlement 的银行账户组（银行名、制式与制式全部字段含账号）不齐时不保存该组，storeId 随组；账号为只写字段，已保存（accountNumberSet = true）且本次未传时沿用已存值、其余字段以本次提交为准。 请求体恰含一个步骤键，且须与 path 的 {step} 一致。完整性按已存值叠加本次提交判定，只写字段（银行账号、Refund PIN）按 accountNumberSet / refundPinSet 判。Business 步所填 Country 在 /config/settlement 的 bankAccountTypes 里无条目（平台不对该国商户出款）时，settlement 步只收 refundPin / confirmRefundPin，bankName / bankAccount / settlementCycle / storeId 不传（传了 → 400 204001），完整性只看 refundPinSet。

  • business：Currency × Country 须是 /config/currencies 里的有效组合；改了币种后 Services 已选方式不在新币种候选内的，在下次保存 Services 时报错。business 步改了 country，且已存结算银行账户的制式与新国家的制式不同（含新国家无条目）时，该账户整组视为未填：读申请不再返回 bankAccount / bankName / storeId，settlement 步要重填。
  • services：所选方式须在 Business 步所选结算币种的候选内；选了线上方式时，Business 的 typeOfOnlineService 必填、为 WEBSITE 时 websiteUrl 必填，缺了在 details 里指向 business.*。
  • settlement：两次 Refund PIN 须一致。
  • documents：按 docKey 绑定上传得到的 fileId，未传的 docKey 保持原绑定，传 null 移除。门店内照、外照在 Services 选了线下方式时才必传；Business 步所填 Country 在 bankAccountTypes 无条目时 docVoidCheque 不必传。

readonlyFields 里的字段服务端忽略写入。

错误码：

  • 204001 字段缺失或格式错，details 逐项指到 <step>.<field>。
  • 204017 结算周期不在候选内。
  • 208003 申请不在 DRAFT / MORE_INFO_REQUIRED，不能保存。
  • 208046 工作人员代为建档的申请（assistedOnboarding 为 true），向导里只读。
  • 208040 documents 步引用的文件不存在、不是本商户上传的或用途不符，details 逐项指到 documents.<docKey>。

单个步骤的字段体

= 1 properties
object (ContactStep)

Step 1 Contact。姓名、职务、电话是 Owner 的账号资料：本步回显当前值、可修改，保存即写回账号资料；哪些字段只读看申请的 readonlyFields。referredBy = Moneris（大小写不敏感）时 monerisMid + monerisManagerName 必填。

object (ServicesStep)

Services 步（向导第 3 步）；至少选 1 个支付方式——该 ≥1 是提交完整性、不是本形状的约束：由服务端在 mode=next 校验，草稿态可为空。

object (BusinessStep)

Business 步（向导第 2 步）。Currency × Country 有效组合以后端配置为准；Services 步选了任一线上支付方式时 typeOfOnlineService 必填、为 WEBSITE 时 websiteUrl 必填（在 Services 步保存与提交时校验）。

object (SettlementStep)

Step 4 Settlement。

  • refundPin + confirmRefundPin / bankAccount.accountNumber 均 write-only 输入、绝不在响应回明文；read 走掩码 + 已填标志（bankAccount.accountNumberMasked / accountNumberSet / refundPinSet）供跨设备恢复。
  • refundPin 两者须一致否则 400（格式见 RefundPin）。
  • Legal Business Name 的核对回显由前端直接读 steps.business.legalBusinessName（不重复为独立字段）。
  • Business 步所填 Country 在 /config/settlement 的 bankAccountTypes 里无条目（平台不对该国商户出款）时，本步不采集 bankName / bankAccount / settlementCycle / storeId，只收 Refund PIN。
object (DocumentsStep)

Step 5 Documents。docIncorporation / docOwnerId / docVoidCheque 必传；docStoreInside / docStoreOutside 在 Services 步选了线下支付方式时必传；docOther1 / docOther2 可选。绑定按 fileId。

上传入驻文档（随 documents 步保存时绑定）

返回的 fileId 在保存这个商户的 documents 步时绑定到具体文档位。

提交审核

校验全部步骤与必传文档（营业执照、Owner 证件、Void Cheque；选了线下方式时加门店内照、外照；Country 在 /config/settlement 的 bankAccountTypes 无条目时不要 Void Cheque、204002 不因它触发）后，申请从 DRAFT / MORE_INFO_REQUIRED 进入 UNDER_REVIEW，同时清空待补项。 首次提交发「申请已收到」邮件，补料重提不发。提交时先做开通准备（按所选支付方式建签约与费率），成功后申请才进入 UNDER_REVIEW；开通准备暂时没做成（可稍后重试的失败）回 503，申请未提交、状态不变，重发本请求即可。申请已是 UNDER_REVIEW 时再次提交返回 204、不做任何事、不重发邮件。

错误码：

  • 204001 字段缺失或格式错，details 逐项指到 <step>.<field>。
  • 204002 必传文档不全，details 指到 documents.<docKey>。
  • 204017 结算周期不在候选内。
  • 208003 申请状态不可提交。
  • 208046 工作人员代为建档的申请（assistedOnboarding 为 true）不在这里提交，由 Owner 在确认邮件里的确认页签署。
