商户后台 商户入驻 — 前端契约面 (0.15.0)

Download OpenAPI specification:

商户后台前端消费的 5 步入驻向导 / 草稿持久化 / Documents 上传 / 提交审核 / 审核状态分流 契约。 入驻申请单（Application：Step 1-5 字段 + Documents 引用 + missingFields + 状态机 DRAFT/UNDER_REVIEW/MORE_INFO_REQUIRED/APPROVED/REJECTED/WITHDRAWN）在注册邮箱激活成功时已备为 DRAFT，本面从 DRAFT 加载续走、不重建。 Refund PIN（Step 4 采集）为 write-only，绝不在任何响应回显。 字段类型以本契约为准。 幂等/CSRF 口径：① 草稿分步保存（PUT，mode=next|draft 两语义）/ Submit（重放命中目标态返一致）天然幂等，故不挂 Idempotency-Key； Documents 上传非幂等（每次产生新 fileId；未绑定的 fileId 不可用，绑定在 step 保存时按 docKey 覆盖）。 ② cookieAuth 的非安全方法一律挂 X-CSRF-Token（double-submit）。 ③ Add Merchant 创建端点不在本面（由商户实体能力承载）；创建后前端切当前商户，本面经 GET /onboarding/application 加载已建草稿续走向导。 ④ 向导渲染所需的全部动态配置（各步的候选集 / 费率 / 有效组合 / 前端拦截参数）见 GET /onboarding/config —— 键清单以该接口自身说明为准。

onboarding-wizard

5 步入驻向导：加载当前入驻申请草稿 + 字段 + missingFields + 状态（GET）；分步保存草稿 + 返回 validationErrors（PUT）；Review 页 Submit 提交审核（POST，DRAFT/MORE_INFO_REQUIRED → UNDER_REVIEW）。

加载当前 Application 草稿（状态 + 各 step 字段 + missingFields + 绑定文档）

加载当前选中商户的入驻申请草稿（注册邮箱激活时已备为 DRAFT，或 Add Merchant 时已备新 DRAFT）。 本接口只加载、不创建：Step 1 Contact 预填注册时已有字段（已预填字段只读）+ Merchant ID。 merchant 上下文从会话当前选中商户取、不信请求体；多份申请按当前选中商户独立返回。 文档预览保证：documents 里返回的每份文档**必带 previewUrl**（短时效内联展示地址），跨会话续填与补料回流时据此回显缩略图； 本次会话刚直传、尚未随 step 保存的文件不在本结果里，其预览由前端用本地文件出。 missingFields 仅在 MORE_INFO_REQUIRED 时非空（由审核动作写入；只承载字段 key + 所属 step，不携带审核原因）。

分步保存当前 step 字段到草稿（校验失败返 400 + 字段级 validationErrors）

分步保存单个 step（Back/stepper 返回不触发后端保存）。两种语义由 mode 区分：next = 校验当前 step 完整后保存 + 推进（校验失败 → 400 + ErrorEnvelope.details〔field-level validationErrors〕，不写持久化 missingFields）；draft = 离开前持久化未完成草稿（放宽必填、仍校验已填字段格式，不推进）。 请求体恰含一个 step key 且须 == path {step}（不一致 → 400）。mode=next 的完整性按已存值叠加本次提交后的结果判定——write-only 凭据字段（accountNumber / refundPin / confirmRefundPin）按 accountNumberSet / refundPinSet 判，跨设备恢复后前端无明文也不必重输。不挂 Idempotency-Key。 Documents step：按 docKey 绑定上传返回的 fileId；要移除某份已绑定文档，把该 docKey 显式传 null（上传成功但未保存 / 已移除的 fileId 不绑定、不可用）。 绑定时校验文件是否已就位，两种失败可辨： 确定未就位（第二步直传未完成 / 被存储端拒收）→ 400 FILE_NOT_IN_PLACE (204014)，整个 step 保存被拒、不静默丢弃该文档；终态、不可原样重试：须重新申请直传目标（得到新 fileId）并重新直传，再以新引用保存——不要向原目标补传（直传目标是一次性的，提交失败即作废）。 本次保存可携带多份文档，故 ErrorEnvelope.details[].field 逐条给出未就位的 docKey（如 docVoidCheque），前端据此只重传出问题的那几份、其余 fileId 原样再提交一次。 暂时无法判定（上游不可达 / 超时）→ 502 / 504，不必重传文件，可原样重试本次保存。 预填 / 来源锁定 / 继承只读字段（Step 1 已预填项 / Merchant ID / Branch 继承身份字段）服务端忽略写入（保持只读）。 仅 DRAFT / MORE_INFO_REQUIRED 可保存；其余状态草稿冻结 → 409。 Refund PIN 经 settlement step 的 refundPin + confirmRefundPin 采集，write-only、不在任何响应出现。

Review 页提交审核（DRAFT / MORE_INFO_REQUIRED → UNDER_REVIEW）

从 Review 页提交：校验所有字段 + 5 必传 Documents 完整 → Application 迁移到 UNDER_REVIEW（DRAFT / MORE_INFO_REQUIRED → UNDER_REVIEW），返回一次性提交确认（刷新后转审核状态页）。 application-received 邮件仅首次提交（DRAFT → UNDER_REVIEW）触发；补料重提（MORE_INFO_REQUIRED → UNDER_REVIEW）不重发 application-received，且同时清空 missingFields（防残留）。 天然幂等：一致重放（已 UNDER_REVIEW 再 Submit）→ 返当前态 200、不重复触发邮件；其余源态（既非可提交态、也非已 UNDER_REVIEW）→ 409 208003； 字段或 Documents 不完整 → 400（204001 字段 / 204002 文档）。 本端点一次校验全部 5 个 step，故 details[].field 用 step-qualified 形式 <step>.<field>（如 settlement.transitNumber，同 readonlyFields 的写法、避免跨 step 同名碰撞）； 前端据此把错误条与 stepper 上的 step 编号关联、点击回跳对应 step。文档类缺失给 documents.<docKey>。

documents

Documents 上传：Step 5 的 5 必传 + 2 可选 Other 文档。文件由浏览器直传对象存储、不经本面——本面只签发直传目标（upload-targets）；提交成功后前端暂存 fileId，绑定到申请单发生在 step 保存（PUT steps/documents）。

取得文档直传目标（浏览器据此直传，文件不经本接口）

上传分两步。第一步调本接口，用声明值（用途 / 文件名 / 内容类型 / 大小）换一个直传目标； 第二步由浏览器把文件连同目标中的 fields 一起提交到 action，文件字节不经过本接口。 本接口不需要知道这份文件将放进哪个 docKey——那是保存那一步的事；本步只按用途签发落点。 允许的格式与大小上限见 purpose 的用途表；声明值不合规 → 400 FILE_DECLARATION_REJECTED (204015) 且不签发目标——换一个合规的文件再申请，同一文件重试无用。 非幂等：每次调用产生新 fileId（重试不复用、不挂 Idempotency-Key）。 本接口只签发目标、不绑定——提交成功后前端暂存 fileId，绑定发生在 Documents step 保存（PUT /onboarding/application/steps/documents）。

onboarding-status

审核状态 + 登录后页面分流数据 + 拒绝结果（粗分类；申诉入口由前端统一客服配置提供）；按当前选中商户的申请状态返回。只读。

审核状态 + 登录后页面分流数据 + 拒绝结果（按当前选中 Merchant）

登录后页面分流真相源：返回当前选中商户的申请状态 + 前端应路由到的业务页面 （入驻向导 / 审核状态页 / 拒绝结果页；商户后台首页 / 商户切换器由商户实体能力承载）。 UNDER_REVIEW 返回审核状态 + 提交时间（审核 SLA 固定 2-3 工作日 = 前端 i18n 固定文案、不返）；REJECTED 返回粗分类拒绝原因（不含细节），申诉入口由前端统一客服配置提供、不随申请状态响应返回。 只读。merchant 上下文从会话取；切换器选另一商户后重新调本接口按那个商户状态分流。

stale-tab 一致性守卫（读写统一）：页面预期的当前商户 ID。与会话当前商户比对，一致才执行；不一致时读不返回错商户数据、写不执行，并按下面两种情形二分： ① 会话有当前商户、只是与 expected 不同 → 409 · 208001（MERCHANT_CONTEXT_CHANGED），响应 context.currentMerchantId 回显服务端当前商户供前端直接 re-sync； ② 会话没有当前商户（无可回显者）→ 409 · 208022（MERCHANT_NOT_ACCESSIBLE），前端重跑启动链路按 routeTo 分流（见 API 基础约定「merchant scope + stale-tab 守卫」）。 挂在所有依赖当前商户的读 + 写接口；前端统一 interceptor 发送 + 处理 409（提示并刷新当前商户）。 豁免：不依赖「当前商户」的接口——当前商户的 re-sync / 切换入口本身，以及目标由 path 直接指定、与当前商户无关的接口。 某个接口挂没挂本 header，看该接口的 parameters 即可（挂了就是必带）。

onboarding-config

向导动态配置：各步的候选集 / 费率 / 有效组合 / 前端拦截参数，一处给全（键清单见该接口说明）。只读、驱动前端渲染。

加载向导动态配置（支付方式 + 费率 + Currency×Country 有效组合 + 级联）

前端渲染向导所需的动态配置（列表 / 费率 / 可选性 / 有效组合由后端配置动态提供）： 本接口是向导所有动态配置的唯一入口，按 Step 给全：Step 1 / 3 电话区号候选（phoneCountryCodes）；Step 2 各营业场景可选支付方式 + 展示费率 + 可选状态（paymentMethods）；Step 3 有效 Currency × Country 组合（currencyCountries）、Industry→MCC 级联（industries）、时区候选（timeZoneOptions，按 country 分组）；Step 4 结算周期候选档位集（settlementCycleOptions）；Step 5 文件上传的前端拦截参数（documentUpload）。这些候选集一律由后端配置决定、前端不要 hardcode。 按当前选中商户上下文返回（不同商户可用集可能不同）。前端渲染用；Step 2/3 有效性以 Next/Submit 时服务端重新校验为准（不信客户端缓存 config）。只读、可缓存。
