商户后台 注册登录与认证 — 前端契约面 (1.0.0)

Download OpenAPI specification:

商户后台 React SPA 消费的注册 / 登录 / 会话 / 账户安全 / 团队成员 契约。 浏览器持 httpOnly 会话 cookie（登录后 set-cookie），字段类型与校验规则以本 spec 各字段为准。

幂等/CSRF 口径:

  • ① 创建类(注册/建成员)与非天然幂等 / 有副作用的写(如改密〔失效会话〕、改成员)挂 Idempotency-Key;
    • 真正天然幂等的纯 PUT/DELETE 可不挂;
    • 认证类(登录/登出/MFA/扫码)与多步 OTP 挑战类(改邮箱/找回)按流程语义不挂幂等键(每次都应重新认证/校验);
    • 例外:找回流程的 factor-verification 步骤挂 Idempotency-Key(该步幂等、重放同键返回同一 resetToken,杜绝网络重试因 OTP 已消费假失败)。
  • ② cookieAuth 的非安全方法一律挂 X-CSRF-Token(double-submit,fail-closed);公开端点(security:[])无会话故无 CSRF。

registration

自助注册与邮箱激活：提交注册建 PENDING_VERIFICATION 账号并发验证邮件，确认页主动点击激活；含重发验证邮件。

注册表单可选值域（电话区号候选）

注册表单渲染所需的候选值集。本端点无需登录、也不需要当前商户——注册页上的人尚无账号，这是它能取到区号白名单的唯一入口。

phoneCountryCodes 的 dialCode 用于渲染区号下拉：前端不要 hardcode 区号表，部署会调整白名单。 回显已有号码时，用同一份候选对整串做最长前缀匹配拆出区号与正文号 （电话在本面是国际格式整串、无独立区号字段，见 Phone）。

入驻向导与商户资料编辑各有自己的候选集端点（getOnboardingConfig / getBusinessInformationOptions）， 取的是同一份部署白名单、形状同为 PhoneCountryCode；本端点只服务注册表单。

Owner 自助注册（创建 PENDING_VERIFICATION 账号 + 发验证邮件）

提交注册：创建 PENDING_VERIFICATION 账号，并发起 Verify Email 邮件的异步发送（邮件投递失败不阻塞注册、账号仍建成）。

邮箱已被占用分两种、结果完全不同：

  • ① 该邮箱已有一个尚未验证的账号 → 200（不是错误）+ 与 201 同一个响应体：不新建账号， 前端回到「等待 Email 验证」页、用响应里的 maskedEmail 与 resendCooldownSeconds 渲染提示与 Resend 按钮（别提示「换个邮箱」——那正是用户自己的邮箱）。
  • ② 该邮箱已是一个可登录账号（已验证 / 已激活）→ 409·968001，此时才提示换邮箱或去登录。

用 HTTP 状态区分即可，200 / 201 对前端是同一段渲染逻辑（要区分「新建了还是本来就有」看 201 vs 200）。

幂等：必带 Idempotency-Key。同键 + 同请求体重发返回同一受理结果、不会重复注册——网络重试请复用同一个键；改了请求体就必须换新键，沿用旧键改内容 → 409·208005。

邮箱激活（确认页主动点击触发的 POST；防扫描器 prefetch）

校验一次性验证 token（仅在激活成功时消费;之前失败不消费、可用同 token 重试,避免卡在待验证但 token 已失效）→ 激活账号 → ACTIVE。

token 单次有效、消费后绝不再签发会话（防旧验证链接泄露后被换取会话）。

已使用 token 重试 → 410,按 ErrorEnvelope.code 细分:已激活 → AUTH_REGISTRATION_ALREADY_ACTIVATED（FE 跳登录页、用户仍须密码登录）/ token 无效·过期 → AUTH_VERIFICATION_TOKEN_INVALID_OR_EXPIRED（FE 引导重发或重新注册）。两种 410 都不换会话。

验证链接的 GET 确认页是前端路由、不激活账号，故不在本 API。

激活成功即已建会话（本响应 set-cookie），前端走应用启动链路（merchantId / 落地页 / 入驻路由经 getCurrentSession + getOnboardingStatus 取，不在本响应返回）。 激活已提交而建会话失败属服务端错误（返错误体、不返 200）：用户重新点击链接命中 410 已激活 → 按密码登录，激活不回退。

session

登录与会话生命周期：密码登录（MFA 联动）、WeChat 扫码登录、会话校验 / 身份摘要 / 可见菜单、登出。浏览器持 httpOnly 会话 cookie，非安全方法带 X-CSRF-Token。

密码登录（邮箱或用户名 + 密码；MFA 联动；签发 BFF 会话）

邮箱 / 用户名 + 密码认证（clientId 由服务端注入、前端不传）。未启 MFA → 建 BFF 会话（set-cookie）。已启 MFA → 返回 MFA_REQUIRED + 短时 mfaChallenge（不建会话）。

200 只有这两支;凭据正确但不签发会话的三种情形一律是 403 + 各自的码，三条文案都不同、按码分流：

  • 邮箱未验证（自助注册待验）→ 208029（跳「等待 Email 验证」页 + Resend 入口;context.maskedEmail 只用于页面展示, 调 resendVerificationEmail 要的明文邮箱用本次登录表单里的 loginId——走到这一支说明它就是该账号的注册邮箱）;
  • 账号被禁用 → 208027;
  • 商户被停用 → 208028。

账号锁定 → 423·966001。

⚠️ 受邀待设密的员工不在这几支里——该账号还没有密码，任何专属提示都等于用任意密码就能探出它的状态,故与凭据错同一外观走 400·206012; 他手上的邀请邮件本身就是恢复路径（另可请 Owner Resend）。

凭据错（密码错 / 账号不存在，两者同一码不区分、防枚举）→ 400·206012：留在登录表单提示「登录凭据错误」、不要据此推断账号是否存在; 失败计数与节流由后端控制、不回前端（没有剩余次数可显示）——你只按响应处理：被锁定 → 423·966001（等冷却）;被限流 → 429。

登录二次校验（提交 TOTP，通过则签发 BFF 会话）

登录第二步：提交 TOTP，通过则签发会话。

失败按 code 分流——

  • TOTP 错 → 400·206012（留在 TOTP 输入框重输、不跳回登录第一步、不要清空已填状态; 失败计数与节流由后端执行、不回前端，故没有剩余次数可显示——别做计数 UI）;
  • 账号因连续登录失败被锁 → 423·966001（等冷却，文案按该码取）;
  • 挑战句柄过期 / 已消费 / 无效 → 410·966002（回登录第一步重新认证，重输 TOTP 无用）。

签发资格在本步重新裁决、不沿用第一步的结论——账号 / 商户可能在你输 TOTP 这段时间里被停：

  • 账号被禁用 → 403·208027;
  • 商户被停用 → 403·208028（与第一步同码同处置）。

故 TOTP 正确 ≠ 一定建会话;拿到 403 就按码提示、回登录页，别当成「验证码错」重输。
