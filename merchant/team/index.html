商户后台 团队成员 — 前端契约面 (2.2.2)

Download OpenAPI specification:

商户后台 React SPA 消费的团队成员契约：当前商户的成员（列表与角色计数、新增 / 编辑 / 删除、邮箱邀请与重发、微信绑定）与可分配的角色。员工从邮件链接进来的设密、确认新邮箱两个落地页在认证契约。 浏览器持 httpOnly 会话 cookie，字段类型与校验规则以本 spec 各字段为准。

幂等 / CSRF 口径：

  • 建成员、改成员挂 Idempotency-Key，同一次提交的网络重试用同键返回首次结果；天然幂等的纯 DELETE 不挂；重发邀请与微信绑定按流程语义不挂。
  • cookieAuth 的非安全方法一律带 X-CSRF-Token。
  • 当前商户以会话为准；当前商户不可访问时返回 409·208022。
  • 路径里的 operatorId 不存在或不属于当前商户，一律返回 403，不区分 404。
  • 多角色：一个员工可以持多个角色，有效权限点取所持各角色权限点的并集；可见分区的可选项随之取各角色模块的并集。
  • 角色的权限边界：逐个角色判，每个角色的权限点集合都必须是操作者在当前商户有效权限点集合的子集（可以相同），Owner 角色恒不可分配。例如只持 Developer 角色的操作者分配不了 Employee：Employee 含商品链接、设备等收款产品分区的权限点，Developer 没有。这条边界用在三处，都由服务端校验：新建成员给的每个角色、编辑成员改成的每个角色、以及被编辑或删除成员现有的每个角色（不能对权限比自己宽的成员改昵称、改可见分区、重设密码、改登录名、改角色、删除、绑定或解绑微信、重发邀请）。操作者改自己这一行时，自己现有的角色总在边界内（Owner 改自己亦然）。Owner 行只有 Owner 本人能编辑，其他操作者即便权限点与 Owner 相同也拒绝（403·906003）。listAssignableRoles 按同一规则返回候选，不满足时 403·206013。Owner 对所有可分配角色都满足。

成员

成员：列表与角色计数、新增 / 编辑 / 删除、重发邀请、微信绑定。

成员列表角色快捷筛选的各项与计数

成员列表顶部角色快捷筛选的各项与计数（各项用法同 QuickFilterCounts，但本端点另给 total、各项可重叠）。value 原样回传给 listTeamMembers 的 roleId；本端点不接受 roleId，其余筛选（按显示名 / 邮箱搜索）与列表一致。

项集不按操作者的权限边界收窄（与 listAssignableRoles 不同）：在册成员持有的每个角色各一项（含已停用的角色），另加当期无成员的可分配角色（count 为 0）以及 Owner（Owner 不在 listAssignableRoles 里，但成员列表有这一行）。label 是角色名，随管理后台维护的角色配置走。

成员可持多个角色，各项计数可重叠，All 取 total。

新建员工（邮箱 → 邀请中、发邀请链接 / 用户名 → 设初始密码、直接可用）

按登录名形态分两支：是合法邮箱格式的为邮箱，不带密码，建邀请中（INVITED）的成员并发邀请设密链接；其余为用户名，由建号的人设初始密码，直接建可用（ACTIVE）的成员。员工归属当前商户（在主商户建的能切换到名下的关联商户，在关联商户建的只在本商户）。角色可以给一个或多个，不可选 Owner 角色。

登录名属于已删除的账号时（不论原属哪个商户），按新建处理并沿用原账号（历史记录接续）：旧密码、MFA、微信绑定都作废，角色以本次提交的为准；邮箱登录名回到邀请中、重发邀请，用户名登录名用本次给的初始密码。原账号若被运营停用，仍保持停用（返回 DISABLED），只能由运营解除。

幂等基准：Idempotency-Key。同键同请求体重发返回首次结果；同键改请求体返回 409·908003。

错误码：

  • 968001 登录名已被其他账号使用（含其他商户的账号）。
  • 206013 要给的角色里有超出操作者权限边界的（含沿用已删除账号时本次提交的角色）。
  • 904001 roleIds 里有本商户角色目录里没有的 roleId，或用户名形态的 loginId 不满足形状（去首尾空白后 1–64 个字符、不含空白与 @）；details 指对应字段。
  • 908003 同一幂等键被用于不同的请求体。

编辑员工（昵称 / 角色 / 可见分区 / 登录名 / 重设密码，一次提交同步生效）

只提交要改的字段，全部同步生效，要么全成功、要么全失败。各字段的副作用：

  • newPassword：重设该员工密码，其全部会话失效，并给该员工登录邮箱发密码已修改通知（用户名账号不发）；尚未设密的员工（邀请中，含停用前未设密的）不能在这里设密。
  • loginId 为用户名：直接生效。
  • loginId 为邮箱：已激活员工不直接生效，向新邮箱发确认链接，员工在落地页确认（confirmMemberLoginEmail）后才切换，确认前旧邮箱仍有效、新邮箱不占用；同一员工的登录邮箱同时只有一笔改动在途（含员工自己在 My Profile 发起的），再改会顶掉上一笔；该员工账号级冷却内 → 429·208013、不发链接、在途一笔不顶掉。用户名员工填邮箱同此，确认后两种登录名都可用。邀请中的员工改邮箱 = 向新邮箱重发邀请，受邀请重发冷却 → 429·208013。
  • roleIds：该员工在本商户的角色整组换成所给的这组，权限按新角色的并集判定，最多晚一个会话复核间隔生效。

Owner 行只有 Owner 本人能编辑、且只能改昵称；Owner 的密码与登录邮箱由 Owner 本人在 My Profile 改。改自己这一行时不能改自己的角色、邮箱形态的登录名与密码（本人改登录邮箱、改密在 My Profile）。

幂等基准：Idempotency-Key。同键同请求体重发返回首次结果；同键改请求体返回 409·908003。

错误码：

  • 968001 新登录名已被其他账号使用。
  • 206013 改成的角色、或该成员现有的角色里有超出操作者权限边界的（不论本次改哪些字段）。
  • 904001 roleIds 里有本商户角色目录里没有的 roleId，或用户名形态的 loginId 不满足形状（去首尾空白后 1–64 个字符、不含空白与 @）；details 指对应字段。
  • 208003 给尚未设密的员工（邀请中，含停用前未设密的）填了新密码。
  • 208013 改登录邮箱发确认链接或重发邀请时冷却未到；剩余秒数见 context.cooldownSeconds。
  • 908003 同一幂等键被用于不同的请求体。
  • 906003 非 Owner 本人编辑 Owner 行、对 Owner 行改昵称以外的字段，或改自己这一行的角色、邮箱形态的登录名或密码。

删除员工（删后不在列表显示、全部会话失效；Owner 不可删）
