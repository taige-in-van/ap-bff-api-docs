商户后台 通知 — 前端契约面 (0.8.4)

Download OpenAPI specification:

通知前端契约：通知设置页（Email / WeChat 通道总开关、只读 Primary + Extra 邮箱增删〔OTP 验证〕、 WeChat 通知接收方扫码绑定 / 解绑）+ 站内信（顶栏铃铛未读计数、列表 / 详情、已读回执、Dashboard 摘要）。 字段类型以本 spec 为准。 merchant scope 从会话取、不信请求体；全部 op merchant-current-scoped，均挂 MerchantContextGuard（stale-tab 守卫，无豁免）。

notification-settings

通知设置：Email / WeChat 通道总开关 + 接收方管理（Extra 邮箱 OTP 两步、WeChat 扫码绑定会话）。

读通知设置（通道开关 + Email 接收方 + WeChat 接收方）

返回当前商户通知设置聚合：Email / WeChat 通道总开关、只读 Primary（= Owner 账号邮箱， 变更随之即时反映）、已验证 Extra 邮箱列表、WeChat 通知接收方列表（昵称 + 绑定时间，平等、无 Primary/Extra 之分）。 站内信无商户开关（不出现在本聚合）。 生效设置：商户从未配置过通道开关时仍返回 200，两开关取商户已配置值、未配置则一律为开启 （默认开为固定业务规则，不随部署配置变化）；接收方列表独立于开关设置、照常返回已有 Extra / WeChat。

切换 Email / WeChat 通道总开关（关闭仅停投递、配置保留）

设置指定通道总开关。本端点请求体即目标本身：全量覆盖、缺省不代表「保持原样」（enabled 必传）。关闭后该通道不投递，接收方配置保留。 天然幂等（重复置同值 no-op）。站内信无商户开关、不在 channel 枚举内。 首次配置：从未配置过开关的商户首次切换直接成功——未配置的通道视为开启（固定默认）；未被本次修改的通道不受影响（另一通道保持其生效值）；两通道各自独立、互不覆盖。加 Extra / 绑 WeChat 不影响开关设置（接收方独立）。

添加 Extra 邮箱第 1 步——向候选邮箱发送 OTP

对候选 Extra 邮箱发起 OTP 挑战：服务端规范化（去首尾空格 + 大小写归一）→ 格式校验（非法 → 400，不发码）→ 去重校验（与 Primary 或已有 Extra 重复 → 409 208012）→ 发 6 位验证码到该邮箱（异步外发； 外发受理未确认 → 502/504——非最终发送失败、不新增 Extra、可稍后重试）。 有效期 / 重发冷却 / 尝试上限为部署可配业务参数；冷却窗口内重复请求 → 429。 按多步挑战流程语义不挂幂等键（每次发新挑战，仅使同一候选邮箱〔规范化后〕的既有活动挑战失效 〔superseded，验证同 410〕；不同候选邮箱的挑战互不影响、可并行验证）。 本 OTP 只授予通知投递资格，不创建 / 修改员工登录 ID、不构成登录安全凭据。

添加 Extra 邮箱第 2 步——校验 OTP，通过即生效

校验候选邮箱 OTP：匹配 + 未过期 + 未消费 + 未超尝试上限 → 通过则该邮箱（经验证）加入 Extra 列表并生效。 通过时以当前 Primary 重做去重（挑战有效期内 Owner Primary Email 若已改成该候选邮箱）：与当前 Primary / 已有 Extra 冲突 → 不创建 Extra、返 409 208012。开关配置独立、不受加 Extra 影响（见 updateNotificationChannel）。 OTP 错误分类（按挑战生命周期）：错误但可重试 → 400 204010（剩余尝试数走 context.attemptsRemaining〔整数类型〕、details 不承载）；尝试超限作废 → 423；过期 / 已消费失败 / 被同邮箱新挑战替代（superseded）→ 410 （用户侧提示文案统一「验证失败」、detail 不泄露码值比对信息）。 challengeId 未知 / 已清理 / 不属当前商户 → 404（反枚举、不区分成因；处置同 410——回第 1 步重新发起）。 并发竞态下该邮箱已被添加 → 409 208012。OTP 一次性消费；成功重放例外： 同一挑战已验证成功后以同码重试（首次 201 响应丢失场景）→ 重放首次结果（返已创建接收方，不再走 410）。

发起 WeChat 通知接收方绑定（创建绑定会话、返回二维码）

创建 WeChat 绑定会话并返回二维码：会话创建为 PENDING（expiresAt 与二维码 TTL 同源）后才返回 201； 创建失败 → 500、不返回二维码。 SPA 展示二维码并轮询 getWechatBindSession（QR_EXPIRED 既不是终态、也不是失败证据，见该接口说明）。用户扫码授权并在微信内显式确认后绑定即告成立 （扫码本身不构成绑定——确认前一律呈现 PENDING），经轮询可见（同一微信身份跨会话去重合并）； 关页 / 停止轮询不会使已确认的绑定失效。 取消 / 二维码超时 / 扫码失败 → 该二维码不能再扫、不新增绑定、可重新发起；状态枚举里没有「已取消」——用户取消 / 关页只是前端停止轮询，已确认的绑定照常生效。 expiresAt 是二维码的有效期，不是本次轮询的截止时间：到期只表示这张二维码不能再扫，sessionId 在此之后仍可继续轮询（不是一次性查询票），已确认但尚未落地的绑定经由它转 COMPLETED。 按多步挑战流程语义不挂幂等键（可安全重发的挑战资源：重复创建各自独立会话，各自的二维码自然到期）。 微信侧不可用 → 502/504（无降级伪成功）。二维码有效期为部署可配业务参数（以响应里的 expiresAt 为准，不要 hardcode）。 与微信快捷登录绑定解耦。

轮询 WeChat 绑定会话状态

轮询绑定会话：PENDING（未扫 / 已扫未确认 / 已确认但结果尚未落地——三者对前端表现一致）/ COMPLETED（绑定完成，必携接收方）/ QR_EXPIRED（二维码不能再扫）。 QR_EXPIRED 纯时间派生（PENDING 且 now > expiresAt）；用户取消 / 关页只是前端停止轮询。 已在微信内完成的确认不会因关页 / 停止轮询而丢失——重新打开页面或稍后轮询仍可见 COMPLETED； 上游短暂不可用时轮询可能维持 PENDING，前端按 PENDING 处理、不必视为失败。 QR_EXPIRED 不是终态：用户若已在微信内确认、只是结果尚未落地，会话可能先呈现 QR_EXPIRED、随后转 COMPLETED （已确认的绑定不会因二维码过期而作废）。由此给消费方三条保证： ① QR_EXPIRED 不是失败证据——不得据它清理本地状态、也不得据它阻止后续 COMPLETED； ② 只要用户已完成确认，继续轮询即会转 COMPLETED； ③ 何时停止轮询由前端自行决定，停止不影响绑定成立——已确认的绑定会在有界时延内（上界为部署可配业务参数） 出现在通知设置页的 WeChat 接收方列表（getNotificationSettings）。故停止轮询后的正确处置是提示稍后刷新设置页查看， 而不是提示「绑定失败」；仅在确知用户未完成确认（取消 / 未扫）时才提示「请重新扫码」。 除此之外状态不回退；COMPLETED 是终态。 同一微信身份重复扫码不产生新接收方（去重合并）。会话取不到 / 跨商户一律 404（归一，不泄露会话是否存在——同本面其余读接口的反枚举口径）； 404 表达的是「你取不到这个会话」、不是会话态、也不代表绑定未成立——前端应停止本次轮询并按上条 ③ 处置。
