收银台 — 付款人契约面 (2.0.3)

Download OpenAPI specification:

付款人在收银台页面上用到的全部接口。

会话

  • 先调入口接口（openQrcodeCheckout 或 openOrderCheckout）拿到会话令牌，之后每个请求都在 X-Checkout-Session 头里带上它。
  • 入口接口建立或认回会话：
    • 带着本入口的有效会话令牌：认回同一会话（state 不是 PAYABLE 也认回），返回 200、不带 grant；
    • 带着有效的 resumeCode：认回付款前的那个会话（state 不是 PAYABLE 也认回），返回 200 与 grant（为这个会话另给一枚令牌，原来的令牌仍可用）；同时带了会话令牌时以 resumeCode 为准；resumeCode 无效、已用过或已过期时按没带处理；
    • 否则签发新会话，返回 201 与 grant；state 不是 PAYABLE，或需要付款人标识而没拿到（此时带 reauthorizeUrl）时不签发，返回 200、不带 grant。礼卡例外：入口 state 为 INACTIVE、EXPIRED 时照样签发，这样的会话只能用礼卡组接口（见 openQrcodeCheckout）。
  • 除入口接口外，一个请求作用于哪个商户、哪个入口、哪笔订单都由会话决定；请求体里不用带这些标识，带了也不采信。令牌无效或已过期时返回 404，要访问的对象不是本会话能访问的时同样返回 404：订单类接口只能访问本会话的订单；礼卡的「我的订单」与存入支付宝卡包按本会话付款人认订单，规则在各接口说明里。

调用顺序

  1. 入口接口：建立或认回会话，取页面的展示内容；店铺码另返回收款页内容（币种、小费档位、采集项、说明），账单另返回账单内容与采集项，商品、票务另返回页面内容（可售项、采集项、条款），礼卡另返回面值档、买家与收件人采集项、条款。
  2. listCheckoutPaymentMethods：取当前可用的支付方式与各自的总应付。店铺码会话还没有订单时，带上付款人输入的金额与小费；商品、票务会话还没有订单时，带上所选各项的小计；礼卡会话还没有订单时，带上所选面值档的售价。
  3. createCheckoutPayment 发起支付，getCheckoutOrder 查结果。会话还没有订单时，请求体带上本产品那一块（付款人填的金额、选购、采集内容）；选的是带 cardForm 的方式时，另带 card 块。
  4. 商品、票务付款成功后的凭证，礼卡的发放状态与凭证，都在 getCheckoutOrder 返回的 sales 里。

付款人可用 deleteCheckoutSavedCard 删除自己的一张已存卡。

礼卡另有三组接口：买家邮箱验证（requestGiftcardEmailOtp、verifyGiftcardEmailOtp）、「我的订单」（listGiftcardOrders、getGiftcardOrder）与存入支付宝卡包（createGiftcardAlipayPass）。

金额

入口返回的标价、售价不含客户服务费；付款人应付的总额以方式列表给出的总应付为准。

金额是最小币种单位的整数字符串，连同币种组成金额对象；只有付款人输入的金额与小费（方式列表的查询参数、店铺码的 storeQr 块）不带币种、只传整数字符串，币种即入口返回的币种。时刻一律是 UTC。

错误

错误响应体都带整数 code。接口说明里点名的 code 按它分流，各自怎么处理写在该接口的说明里；没点名的通用错误（400 参数校验、404、429 等）按 HTTP 状态码处理，不必认它的 code。

进入收银台

进入收银台：用静态码（店铺码、账单、商品 / 票务 / 礼卡链接）或订单链接（动态码、开放 API 托管页、电商插件订单）建立或认回会话，返回这个入口的展示内容。

用静态码进入收银台（建立或认回会话）

静态码入口（店铺码、账单、商品 / 票务 / 礼卡链接）：按顶部「会话」一节建立或认回会话，返回这个入口的展示内容。礼卡入口的 state 为 INACTIVE、EXPIRED 时也签发会话。

state 按产品给出：

  • 店铺码：码已停用，或商户当前不能用店铺码收款为 INACTIVE，其余为 PAYABLE；
  • 账单：已付清为 PAID，已过 invoice.expiresAt 为 EXPIRED，商户当前不能用账单收款为 INACTIVE，其余为 PAYABLE；
  • 商品、票务：链接已停用或商户当前不能收这一产品为 INACTIVE，其余为 PAYABLE；
  • 礼卡：链接已停用或商户当前不能收这一产品为 INACTIVE，已过活动截止日为 EXPIRED，其余为 PAYABLE。

码已删除（含账单已删除）时，带着有效会话令牌或 resumeCode、且该会话已有订单的照常认回，state 为 INACTIVE；编号不存在，或码已删除而没有可认回的会话，返回 404。

不需要幂等键：重复调用不会产生重复的业务后果。

用订单链接进入收银台（建立或认回会话）

本会话订单

本会话这笔订单：可用支付方式与各自的总应付、发起支付、查状态，以及付款时可选的已存卡。

读当前会话订单的当前状态

本会话那笔订单此刻的状态、金额构成与所用方式，可反复调用。nextAction 只返回本会话发起的那次支付的拉起动作，与发起支付时给的是同一个，可重复取。订单已过到期时刻而状态尚未更新时按 EXPIRED 返回。

商品、票务的凭证与礼卡的发放状态、凭证在 sales 里，返回条件见各字段。

本会话还没有订单（店铺码、账单、商品、票务与礼卡会话在发起支付之前）→ 404。

列出该会话当前可用的支付方式与各自的总应付

当前可用的支付方式，按本次请求的受理环境与这个收款入口允许的方式给出；列表是此刻的结果，发起支付时会再校验。商户下单时指定了支付方式的订单，列表只含那一项（它在当前环境不可用时为空）。

每项带选这一方式时的总应付，发起支付时会重算；此刻算不出总应付的方式不出现在列表里。没有可用方式时返回 { items: [] }，不是错误；礼卡会话还没有订单而 state 不是 PAYABLE 时同样返回空列表。

会话还没有订单、金额由付款人选定时（店铺码、商品、票务、礼卡），用 amount（店铺码另有 tip）传付款人当前的选择，各项总应付按它算；还没选时不传。tip 只对店铺码采信，其他产品带了不采信。会话已有订单，或金额已定（账单与订单入口），传了也不采信。采信时格式不对，或商户没开小费却带了 tip，返回 400。

发起支付

以所选方式发起支付，返回订单此刻的状态与拉起动作，形状同 getCheckoutOrder，最终结果以它为准。请求体怎么带见 CheckoutPaymentRequest。一个会话只有一笔订单，换方式、失败后重试都在这笔订单上。

请求体不合规（见各字段说明）返回 400，details 指到字段。之后按顺序判：

  1. 本会话订单已是终态（已过 expiresAt 而状态还没更新的按 EXPIRED）：不发起，返回 200 与该终态；
  2. 本会话发起的同一方式（带 cardForm 的方式还要是同一张卡）那次还在等付款人完成、且原拉起动作没过渠道给的有效期：返回 200 与原来的拉起动作；过了有效期按新发起往下判；
  3. 以下情况拒绝，不建订单、不占库存、不发起支付；都不命中则发起，返回 201。
  • 店铺码：商户当前不能收这一产品 108200；
  • 商品、票务、礼卡的链接已停用或已删除，账单已删除，或商户当前不能收这一产品 108300；
  • 账单已付清 108301，已过到期时刻 108302；礼卡已过活动截止日 108303；
  • 会话还没有订单时另判：商品、票务所选某项不在销售期 108303、余量不够 108304；礼卡所选面值档已售罄 108304，已达张数上限 108307，已达累计面值上限 108308（context.purchaseLimit 带上限），本付款人在这条链接下有一笔已付款、因买家邮箱没验证而没发放的订单 108309（先验证邮箱），付款人或本次填的买家、收件人邮箱在礼卡购买黑名单里 108325（不带 context，detail 不含原因）；
  • 页面显示的总应付与服务端此刻重算的不一致 108103（context.payable 带此刻的总应付）；所选方式已不在当前可用方式里（含此刻算不出这一方式的总应付）108102；card.savedCardId 不是本会话付款人在这一方式下可用的已存卡 108107。

这笔付款无法受理时 status 为 REJECTED、不带 nextAction，不给原因。

商品、票务、礼卡会话首次发起时，Accept-Language 所示语言记为付款人的下单语言，凭证与收据邮件按它发。

不需要幂等键：同一会话内重复提交不会多下一笔订单。

礼卡

礼卡专用：买家邮箱验证、「我的订单」与存入支付宝卡包。

给买家邮箱发验证码

给一个邮箱发验证码，返回 challengeId；码在 verifyGiftcardEmailOtp 提交。只在礼卡会话可用（state 为 PAYABLE、INACTIVE、EXPIRED 都行），其余会话 404。

礼卡链接已删除时，只有已有订单的会话可用（还没有订单的会话 404），且 email 只能是这笔订单的买家邮箱，不是它走通用 400。

  • 重发 = 冷却结束后再调一次，拿到新的 challengeId，旧码作废；冷却中再调 → 429·108324，剩余秒数在 context.cooldownSeconds。
  • 验证码的有效期与重发冷却随返回的 expiresAt 与 cooldownSeconds 给出。同一邮箱与同一会话的发送次数有上限，超出时返回通用 429。
  • 邮箱格式不对走通用 400。

按挑战流程语义不带幂等键。

提交验证码验证买家邮箱

提交邮件里收到的验证码，challengeId 取自 requestGiftcardEmailOtp 的返回。只在礼卡会话可用（state 为 PAYABLE、INACTIVE、EXPIRED 都行），其余会话 404；礼卡链接已删除时只有已有订单的会话可用（发码时已限定为这笔订单的买家邮箱）。

验证通过后：

  • 这个邮箱记到本会话付款人名下；会话此前认不出付款人的，从此认得出（就是这个邮箱对应的付款人）；
  • 这条礼卡链接下买家邮箱是它、还没有付款人的订单归到本付款人名下，之后出现在「我的订单」里；
  • 本付款人名下因为这个邮箱没验证而没发放的礼卡订单随即继续，发放状态在 getCheckoutOrder 或「我的订单」里查；别的付款人名下的订单不受影响。

验证码：

  • 不对、还有尝试次数 → 400·104303，剩余次数在 context.attemptsRemaining，留在原处重输；
  • 这个挑战已过期、已用过或不存在 → 410·106300，重新发码，重输无用；
  • 错的次数用完、这个挑战作废 → 423·106301，重新发码。

验证通过后挑战即用掉，再提交同一个 challengeId 返回 410·106300。按挑战流程语义不带幂等键。

我的订单：付款人在这条礼卡链接下已付款的订单

把一笔礼卡订单的凭证存入支付宝卡包

可操作的订单：本会话的订单（会话认不出付款人时也可以），或本会话付款人在这条礼卡链接下的已付款订单（认订单的规则同 getGiftcardOrder）；其余 404。礼卡链接已删除时只有本会话的订单可用。

不需要幂等键：不改订单与凭证。
